## PF-1 (fixes P0-1 + P0-2): time-weighted risk statistics

```
Read CLAUDE.md first. In frontend/src/utils/calculations.ts, computePortfolio currently
derives monthlyReturns, annualizedVolatility, maxDrawdown, annualReturns (and App.tsx
derives rolling returns) from `cumulativeValues`, which includes monthly contribution
cashflows. That makes volatility/annual/rolling returns overstated and drawdowns masked
whenever monthlyContribution > 0. Two failing tests in
frontend/src/utils/calculations.audit.test.ts ("KNOWN DEFECTS" describe block) prove it:
- "FINDING: volatility should be 0 for flat prices with contributions"
- "FINDING: max drawdown should reflect market losses, not be masked by contributions"

Fix: inside the sim loop, after adding the month's contribution and applying price
growth, record the month's TIME-WEIGHTED return:
  twr_i = portfolioValueAfterGrowth / (portfolioValueBeforeGrowth) − 1
where portfolioValueBeforeGrowth is the total AFTER rebalance and AFTER the contribution
is added but BEFORE the price ratios are applied (the loop already has all components —
you'll need to sum holdings right after the contribution step). Chain these into a
TWR index (start 100) alongside cumulativeValues.

Then:
- annualizedVolatility and the monthly-return vector: compute from twr returns.
- maxDrawdown: compute on the TWR index series.
- annualReturns and the rolling-returns input: compute on the TWR index series (add a
  `twrIndex: CumulativePoint[]` field to PortfolioResult and use it in App.tsx's
  rollingData memo). The cumulative chart must KEEP showing the money-weighted
  cumulativeValues (product behavior unchanged there).
- When monthlyContribution === 0 the TWR series is proportional to cumulativeValues, so
  all existing passing tests must stay green unchanged.

Update the two failing tests' expectations only if their hand-computed comments are
wrong (they shouldn't be). Do NOT debounce anything or change slider behavior; keep the
loop O(n·funds) — no extra allocations beyond one Float64Array and one array.

Verify: npx vitest run (the two named tests now pass; all others unchanged),
npx tsc --noEmit (0 errors), npm run build. Then run `npx tsx audit/bench.ts` and
confirm the worst-case p95 stays under 2 ms.
```

## PF-3 (fixes P1-1): IRR contribution timing

```
In frontend/src/utils/calculations.ts, calcAnnualizedIRR receives cashflows built in
computePortfolio (lines ~204-210) as:
  cashflows[0] = -initialValue
  cashflows[i] = -contribution   for i in 1..n-2
  cashflows[n-1] = -contribution + finalValue
But the simulation adds the contribution for step i BEFORE applying the price change
from dates[i-1]→dates[i] — i.e. the money is invested at time i−1, not i. The failing
test "FINDING: IRR should discount contributions when they are invested, not one month
later" in frontend/src/utils/calculations.audit.test.ts shows the resulting upward bias
(fixture: true 213.8% vs reported 257.5%).

Fix: build the cashflow vector so each contribution is discounted at the period the sim
invests it:
  cashflows[i] = -contribution for i in 0..n-2 (added on top of cashflows[0] = -initialValue at i=0)
  cashflows[n-1] = +finalValue
(n-1 contributions total — same count as the sim, one at each of times 0..n-2.)
Sanity-check against the failing test's hand math: 2 dates, P=10000, c=1200, ×1.1 →
cashflows [-11200, +12320] → monthly IRR exactly 10%, annualized 1.1^12−1.

Keep Newton's method but add a safeguard: if it fails to converge or produces r <= -1,
fall back to bisection on (-0.99, 10). Do not change any other stat.

Verify: npx vitest run — the named test now passes; the other audit tests
(contributions/capital-invested, benchmark mirror) stay green. npx tsc --noEmit,
npm run build.
```
